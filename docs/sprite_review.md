## 2. 主角接错模型的原因

### 2.1 必须区分模型编号、完整 type 字节、CHR bank

NPC 的 `type` 字节包含两个字段：

```text
direction = type & 3
model     = type >> 2
```

因此 `type=0x24` 表示 `model=0x09, direction=0`，不能直接把 `0x24` 当成模型编号。CHR bank 又是另一类参数，决定编号
`0x80..0xff` 的图块来源。

编辑器 `TileSetHelper.parsePlayerMoveImage()` 的注释及示例涉及 `0x24` 和 `0x94`
，但该函数是把外部图片写回图块数据的辅助逻辑，其注释不能代替当前 ROM 的主角初始化证据。之前把这些值直接传给模型解码器是错误的。

当前 ROM 的 PRG bank `0x1a`、CPU `$A127`、文件 `$34137` 包含步行角色初始化表：

```text
09 0b 0d    步行角色模型
35 36 37    另一组状态下的模型
```

同一段初始化代码把表项写入 `$0360` 系列状态。FCEUX 的 `opening-state/cpu_009300.bin` 中 `$0360=09`，与
ROM 初始化相符。模型 `0x09` 的正面、背面轮廓也与工程原有 `sprite_player` 完全一致。

### 2.2 修改后的运行路径

```text
Character.bitmapId = 9
Character.currentBitmap()
  → decodeSprite(0, bitmapId, direct, halfStep, frame)
  → 固定 CHR bank04/05
  → 当前方向和步态的四个8×8图块
  → NES颜色映射
  → 256字节当前帧
  → 原 indexed framebuffer 透明绘制
```

模型 `0x09` 全部八个姿态都只使用固定 `04/05` 图块，因此这里的动态 bank 参数不会影响主角；没有让主角再依赖
`0x94/0x95`。

修正位置：[character.cpp](../app/src/main/cpp/logic/status/character.cpp)、[character.h](../app/src/main/cpp/logic/status/character.h)。
`bitmapId` 现在实际参与解码，不再被硬编码值绕过。

## 3. 与工程原有精灵的完整对比

### 3.1 原 NPC 贴图

从仓库 `HEAD` 读取原 `sprite_bmp.cpp` 的 135 张图，逐张与新的模型、方向、步态、CHR 配置比较透明轮廓。135
张全部找到像素完全相同的轮廓。

该比较说明图块结构可以对应，不能单独证明业务身份：不同模型、着色板和图块配置可能产生相同轮廓。报告同时保留每张原图对应的
bank、模型、方向和帧，以便进一步核对。

例如原静态图索引 3 对应 `bank64 / model0f / right / frame0`；索引 4、5 对应
`bank64 / model1d / down、left / frame0`。因此原数组索引不能直接当成 ROM 模型编号。

原图见 [original_npcs.png](sprite_previews/original_npcs.png)。逐图对应结果存于开发报告
`metalmax-analysis/sprite-review/review_report.json`。

### 3.2 原主角与 ROM 主角的差异

原主角有独立的四张静态图，运行时再镜像成方向和步态。新图使用 ROM 的实际四向双帧规则。

| 方向 | 第0帧透明轮廓差异 | 第1帧透明轮廓差异 |
|----|----------:|----------:|
| 上  |       0像素 |       0像素 |
| 下  |       0像素 |       0像素 |
| 左  |      32像素 |      46像素 |
| 右  |      32像素 |      46像素 |

侧面原有手工帧与 ROM 帧存在像素差异，不能用原静态图强行覆盖 ROM 步态。新的八帧全部与 ROM 实际生成的
OAM 渲染结果一致。

原独立主角图还用了额外的颜色索引 `109..112`，与 ROM 系统调色板的 RGB 不完全相同。新图保留原 ROM
配色：金色头发、蓝色衣服、肤色和不透明黑色描边；不宣称与原手工图 RGB 完全相同。

## 4. 普通精灵解码与表边界修正

普通精灵使用下列 ROM 规则：

```text
pose = uint8(model_base[model] + direction_offset[direction] + step)
attribute = model_attribute[model] | direction_attribute[direction]

四图块 = 上左、上右、下左、下右
每块独立水平翻转 → 整体水平/垂直翻转 → 对应上下半身调色板
```

相关表的 PRG 段内起点：

| 表       | PRG offset | 用途             |
|---------|------------|----------------|
| `$A597` | `0x34597`  | 方向帧偏移          |
| `$A59B` | `0x3459b`  | 方向属性           |
| `$A59E` | `0x3459e`  | 模型姿态起点         |
| `$A5DD` | `0x345dd`  | 模型调色板及翻转       |
| `$847B` | `0x2647b`  | 图块差值、独立翻转、纵向偏移 |
| `$8552` | `0x26552`  | 上半身图块          |
| `$8629` | `0x26629`  | 下半身图块          |

文件 offset 需要再加 16 字节 iNES header。

编辑器把后三张表声明成 217 字节，代码注释也明确其大小待验证。实际相邻起点差为 215 字节；这些声明不等价于
CPU 的合法索引范围。CPU 用八位 Y 寄存器访问对应 PRG 地址，不受 Java 数组长度限制。

模型 50 的侧面第二帧会访问索引 217。之前把这个索引退回 216，并在参考测试中跳过整个模型，属于人为替代原行为。

现在三个索引表分别保留从原地址开始的完整 256 字节可访问窗口，使用八位索引运算。它们仍存放在原
`sprite_data/pose_table.h` 中，共增加 `3×39=117` 字节。重叠地址的字节按真实 ROM 保留，没有根据“看起来应当像人物”修补数据。

`$847B` 的 bit7 还控制一像素的纵向偏移。`drawSprite()` 现在保留该位置变化；局部 16×16 帧自身不裁掉脚部。

## 5. 特殊模型和系统模型的修正

### 5.1 特殊模型，type=1

原实现存在以下问题：

- `head` 中的偏移被加到坐标，实际 ROM `$9031` 例程执行减法。
- 图块值 0 被当成 CHR tile0 绘制，实际 ROM 省略该 OAM 项。
- 水平翻转按整个图块数组的 `i%2` 处理，奇数宽度会导致下一行的翻转起点错位。
- 仅按编辑器“奇偶图块翻转”描述实现，未复现 ROM `$907F` 的移位模式。

修正后按实际 ROM 规则处理：

```text
x = normal_origin_x - (head & 0x1c)
y = normal_origin_y + 7 - ((head & 0xe0) >> 3)
palette = head & 3
flip_pattern = [00,55,aa,33][attribute & 3]
```

每行重新使用翻转模式，按列移位，并跳过 tile0。上述 `+7` 包括普通精灵原点与 NES OAM 锚点的转换，也计入原例程
LSR/EOR/ADC 的进位行为，不能简单写成 `+8`。

### 5.2 系统模型，type=2

系统模型由多项原始 OAM 数据组成，X/Y 是相对角色锚点的有符号偏移。原数据中的 `f0`、`f8` 等表示 `-16`、
`-8`，之前直接加无符号值，会把图块画到远离角色的位置或屏幕外。

修正后：

```text
x = normal_origin_x + int8(raw_x)
y = normal_origin_y + 3 + int8(raw_y)
```

每项保留水平翻转、垂直翻转和自己的调色板。NES 的 OAM 越靠前，重叠的不透明像素优先级越高；当前字节画布通过逆序绘制保留这个优先关系。

所有运行代码由 [import_reverse.py](../tools/import_reverse.py)
生成到 [sprite_resources.cpp](../app/src/main/cpp/sprite/sprite_resources.cpp)，修正已经写入生成器，重新导出不会丢失。

## 6. 着色板复核

四组精灵着色板的原始 NES 索引来自 ROM 文件 `$7D737..$7D746`：

```text
0f 36 0f 16
0f 36 0f 21
0f 37 0f 18
0f 36 0f 12
```

与编辑器导出及 FCEUX 快照 CPU `$0290..$029f` 一致。导入器现在额外断言导出数据与 ROM 原始 16 字节一致。

映射到现有 256
色索引表后的数据仍存于 [sprite_palette.h](../app/src/main/cpp/sprite/sprite_data/sprite_palette.h)
。CHR 像素值 0 直接转为透明索引 35；其他像素即使使用黑色也保持不透明。不能把黑色与透明区混为一类。

主角上半身、下半身可能使用不同子调色板；垂直翻转时颜色仍跟随源图块。普通、特殊、系统三条绘制路径均经过颜色检查。

工程原 `graphic/palette_data.cpp/.h` 与地图色表未修改，也没有给地图增加另一套调色板。

## 7. NPC 实际上下文与剩余缺口

所有 639 条 NPC 基础记录都进行了模型、类型和 CHR 上下文核对：

| 分类                      | 记录数量 | 当前处理                  |
|-------------------------|-----:|-----------------------|
| 具有现有地图属性及非零模型           |  561 | 按所属地图 CHR bank 生成预览   |
| 非零模型且只访问固定04/05图块的附加组记录 |   11 | 根据真实OAM访问确认，无需猜地图bank |
| model0 控制记录             |   37 | 保留数据，不生成角色图片          |
| 需要动态图块但附加组没有地图上下文       |   30 | 保留原始数据，标记缺口，不生成猜测图    |

地图 0..239 共引用 594 条 NPC 记录；额外组 240..249 共 45 条，缺少同编号 `mapProperties`。其中 4 条为
model0，11 条使用固定图块，其余 30 条需要进一步追踪它们被加载到哪张地图、当时选择什么 CHR bank。

把这些附加组一律当成地图，或默认套 bank64、bank94，都会再次生成错误角色。这部分目前明确作为上下文缺口保留。它们的剧情用途和宿主地图不能仅凭组编号确定。

普通模型完整 atlas 展示的是“模型在指定 CHR 配置下的结果”，并不代表每种模型都能在每种地图使用。特殊模型通用
atlas 也存在这种限制；核对实际 NPC 应查看图集中的逐记录预览，标题列出地图、bank、type 和模型编号。

脚本运行时切换 CHR、场景复用附加 NPC 组，以及 NES 的背景遮挡和扫描线精灵限制，仍属于进一步还原完整场景语义的范围。本次
OAM 测试证明像素合成与原例程一致，不宣称已经模拟全部 NES PPU 行为。

## 8. 验证方式与结果

原验证只将 C++ 输出与编辑器 `TileSetHelper` 输出对比。两者共享同一解释、同一表边界，因此无法发现主角选择错误和编辑器自身未覆盖的语义。

新的 [sprite_reference.py](../tools/sprite_reference.py) 在开发阶段执行原 ROM 的实际 6502 例程：

- bank1a `$A57A`：生成姿态及属性。
- bank13 `$835C`：生成普通精灵 OAM。
- bank13 `$9031`：生成特殊模型 OAM。
- bank13 `$8000`：生成系统模型 OAM。

工具只实现这些例程使用的指令子集，指令数量有上限，遇到未知 opcode 或不允许的写入立即失败。输出 OAM 后，再按
NES CHR 和精灵颜色光栅化。它不调用编辑器图片合成器，也不使用原生解码公式生成期望值。
